**核查中额外发现、文档尚未利用的三件事**

1. **`channel_overrides` 的查找顺序是"先精确 channel/thread id，再父 channel/forum id"** —— 子线程会继承父级 override。对私聊无影响，但一旦将来给群配绑定，这个继承行为必须先想清楚。
2. **cron 的 preflight 是一台免费的自检机**：job 点名的 MCP server 若解析不到任何工具，或投递目标没有凭据，job 直接 `blocked_config` + **一次**告警，且不花 token。这比 OQ7 设想的"自己读 Hermes 配置做自检"便宜得多，方向应该反过来：**让 cron 的自检替我们守门**。
3. **`no_agent` 模式**：脚本 stdout 原样投递、零 LLM 参与。见 §4 P1-2。

## 3. 问题清单（按严重度）

### P0-1 没有威胁模型，而"自报身份"被当成了安全护栏

`§3.2` 降级路径与反例 X9 规定：未绑定通道 → Agent 先反问"你叫什么？"→ 得到回答后**照常调用 `as_member="<用户自报的名字>"`**；程序侧只校验"这个名字在 member 表里吗"，并在失败时**返回成员名单**。

后果：**任何能给 bot 发消息的人，说一句"我是妈妈"，就能读到妈妈的待办、改删妈妈的条目。** 从攻击者视角，自报与"猜一个"完全等价，X9 因此不是安全控制。

文档在 R1 结尾承认"Agent 侧的隐私是**协议性**的"——但**承认不等于建模**。

**修法（二选一，都很便宜）**

- **写清威胁模型**（推荐）：在 §0 或 §10 明确声明"家人互信、模型会犯错、**输入内容不可信**、网络侧他人不可达"，并承认在此模型下自报可接受。
- **把断言升级为可验证的断言**：`channel_overrides` 的提示词里除名字外再注入一个**每成员随机 `bind_key`**；工具签名加可选 `bind_key`；程序校验 `name + key → member`。未绑定通道的用户拿不到 key，自报必然失败。成本 = 一个参数；残余风险 = "已绑定通道内模型被提示注入"（写明即可）。但"任何陌生人自称即可读隐私"这个洞被堵死。

**必须同时做的**：Hermes 侧访问控制进上线检查项。微信 `dm_policy` **平台级默认是 `open`**，而 gateway 安全章节又写"默认拒绝未在 allowlist / 未配对用户"——两处表述层级不同，**不要依赖默认值**，显式设置 allowlist（`WEIXIN_ALLOWED_USERS` / QQ 侧对应项）与 pairing，并逐个确认。

### P0-2 真值表只覆盖"行状态"，没覆盖"状态迁移" → **已落地为 V7**

三张表（§4）的行是 list/get/add/update/delete，列是**目标当前**的 owner/ledger。于是：

- `update_event(id=全家日程, owner=某人)` → 把全家日程改造成私人日程，全家看不见了；
- `update_entry(id=共享流水, ledger=personal, member_id=我)` → 把公共支出挪进个人账本；
- `update_entry(id=我的个人流水, ledger=shared)` → **私账一键发布给全家**；
- `update_todo(id=我的待办, owner=别人)` → 归属漂移。

**已在 v0.5.1 修复**：新增 **V7（归属与账本创建后不可变）**，硬塞返回 `DENIED` + "请删除后重建"话术；真值表加"读表前先记住 V7"；§5 补上原先缺失的 `update_entry` 说明；新增反例 **X11–X14**。**v0.5.2 又细化了一次**：`update_*` 的 schema 改为**保留**这些字段、**值不同才拒**（原写法"字段不存在"会让模型只拿到语焉不详的校验错误），并把 `reason:"immutable"` 写进冻结的错误码表。详见 `docs/设计方案.md` §4 / §5.1。

> 这是本次评审中唯一"不修就会真出事故"的一条，因此优先落地。

### P1-1 代记是单向盲写：`created_by` 存在，却没用在权限上

V4 允许代记，但 V1/V3 只认 `owner_id`。所以"我帮妈妈记的待办"**我既看不见、也改不了、也删不了**——写错了只能求妈妈自己删。而 `todo` / `event` / `entry` 三张表都有 `created_by` 字段，完全没参与判定。

**建议**：创建者对自己创建的条目保留**可见权与删除权**（内容本就是他输入的，不增加任何隐私暴露），或在回执里给一个 `undo` 窗口。成本极低，消掉一个必然被家人抱怨的问题。

### P1-2 定时路径还差两块拼图（官方文档直接支持）

- **cron 的 family 工具集必须显式开启**。cron agent 拿的是 `cron` 平台的工具集配置，不是 CLI 默认值；要让 §3.3 的 `get_today` 能被调用，需在 job 的 `enabled_toolsets` 里点名 family MCP。好处是这会触发 preflight：解析不到工具 → `blocked_config` + 告警，**不会静默失败**。此条应写进 D11 与上线检查项。
- **周报/摘要建议改用 `no_agent` 模式**：cron 支持"脚本 stdout 原样投递、零 LLM 参与"。给程序加一个只读 CLI（`family-assistant today --member 妈妈`，复用 domain 层与 P3 话术），cron job 变成 `no_agent + script + deliver: "weixin:<chat_id>"`。**D11 的整个风险类别随之消失**（不再有"prompt 里的字面量有没有被写错/改掉"），且不花 token、不可能算错数字。代价：D1"只做 MCP 服务端"要松一格——值得。

### P1-3 Spike 的统计功效撑不起"100%"

T7 是"同一句话重复 10 次"。**零失败时，真实错误率的 95% 单侧上界 = `1 − 0.05^(1/n)`**：

| 样本量 n | 零失败后错误率的 95% 上界 |
|---|---|
| 10（当前 T7） | **≈ 25.9%** |
| 30 | ≈ 9.5% |
| 60 | ≈ 4.9% |

T1–T4 各只跑一次，更弱。"100%"在有限样本下不可验证，能验证的是"**零次失败 + 残余率上界**"。

**建议**：T7 提到 ≥30 次，**分不同措辞、跨多轮对话、含一次 `/new` 之后**；通过标准改写成"零失败，且样本量足以把错误率上界压到 X% 以下"。真正的风险不是第一轮照抄，而是**长对话中的漂移**——这一点现在没测。

### P1-4 与家人"已经在用 Hermes"的冲突没被处理

`channel_overrides.system_prompt` 是**替换该会话的全局 prompt**，而定位里写着"家人已在用 Hermes"。也就是说，**妈妈那个 chat_id 里原有的个人助理行为会被家庭助手 persona 整体接管**，不只是家庭事务；家庭工具调用与她的其他对话还共享同一份 session/history。

**建议**：给每位成员开**专用 chat / 通道**承载家庭事务；或明确接受接管，并加一条回归冒烟（绑定后问一句无关问题，确认通用能力没退化）。

### P2 契约缺口（可在 §5 一次补齐）

- **响应信封与错误码全集未冻结**。现有 `MISSING_PARAMS` / `AMBIGUOUS` / `DENIED`；缺 `NOT_FOUND`、`INVALID_PARAMS`（X1 说"模型硬塞 owner → DENIED"，但 schema 无此参数时通常是校验错误，行为要定义）、金额非法、**`category.kind` 与 `entry.type` 不一致**等。V7 落地后建议再细分一个 `IMMUTABLE_FIELD`（或至少固定用 `DENIED` + 固定话术）。
- **update 的"置空"语义未定义**：`update_todo(due_date=null)` 能不能清掉截止日期？`undefined` 与 `null` 的区别不写清，实现者一定分叉。
- **金额上限与确认阈值**：模型把 ¥35 传成 350000 没有任何拦截；建议超阈值需回执确认。
- **id 唯一性**：4 位随机段必须靠 DB 唯一约束 + 重试保证，不能靠概率。
- **成员删除语义**：member 删除后其名下数据怎么办（RESTRICT / 软删）。
- **P6 自相矛盾**：`restore_deleted(kind, id)` 正是 P6 禁止的"用 mode 参数把多个操作塞进一个工具"，建议拆成 `restore_todo/event/entry`。
- **语义重叠**：若 `update_todo` 也能改 `done`，就与 `complete_todo/reopen_todo` 形成两条路径（话术可能不一致）。建议 `update_todo` 明确不接受 `done`。

### P2 未评估的替代方案：一个 profile 一位成员

"已评估并否决"里写 `identity_header: profile` 是"静态值，与说话人无关"——在**单连接 / 单 profile** 前提下正确；但官方文档把 **"One agent per family member"** 明确列为多 gateway 的典型用法，且明确"credentials are never shared across profiles"。也就是说：**每成员一个 profile + 每成员一个 family token / `identity_header`，可把身份从"提示词中介"升级为"凭据中介"，R1 整个风险类别结构性消失。**

真正的阻碍不是那句"静态值"，而是：**一个平台 bot 凭据无法服务多个 profile**（微信 iLink 是"全家 DM 同一个 bot 身份"），每成员 profile 需要每成员自己的 bot 凭据——对 QQ/微信是实打实的运维成本。**这个理由才是应该写进"已否决"的内容**；也值得作为 Spike 01 的 Variant B 花半天验证一次，因为一旦可行，V1–V6 就不再依赖模型服从。

## 7. v0.6 追加：身份模型的更换（超出本评审范围）

本评审只指出问题（P0-1），**没有**提供这个答案。v0.6 的身份模型来自对同类实现（同一作者的 `life-assistant` v1 / v2）的考察，记录在此以免日后归错功。

**结论**：身份改由 **Hermes profile（连接级）+ 每成员 family token** 提供（设计方案 D13），工具面**不再有任何说话人身份参数**；D10（通道绑定）、D11（cron 写死字面值）、D12（`bind_key`）全部退役。

| | v0.5.2（`bind_key`，本评审 P0-1 的建议） | v0.6（profile + token） |
|---|---|---|
| 身份载体 | 提示词 → 模型照抄 → 参数 | **连接**（profile 配置里的 token） |
| 冒充他人 | 靠服务端校验密钥挡住 | **结构上不可表达**（没有参数可填） |
| 提示词资产 | root of trust，需与配置逐字 diff | 降级为纯语义 skill，**不含身份** |
| 密钥泄露面 | 密钥明文躺在提示词里（R8） | 密钥不进提示词 |
| 配错 | 降级为匿名或被拒 | **`identity_mismatch` 响亮失败** |
| cron 身份 | 必须写死字面值（D11） | 随 profile 自动确定 |
| 代价 | 无 | **每成员一个 bot 凭据 + 一个 profile**（R10，待实测） |

**新增的最大未知**：**R10**——每位成员各自一个 bot 凭据，在微信 / QQ 上能不能跑通。这是 v0.6 唯一"必须先实测再写代码"的假设；Spike 01 已重写为以它为首项。若不成立，回退 v0.5.2 方案（本评审建议的 `bind_key` 路径保留在设计方案 §3.2 的否决列表里，理由与代价都写着）。

**本评审的结论有没有被推翻**：没有。P0-1（自报身份不是护栏）与 P1-1（代记盲写）在 v0.6 下依然成立、且解决得更彻底；V7（归属不可变）、V8（代记者权利）与 §5.1（契约冻结）不受身份模型影响。
