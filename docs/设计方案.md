# 家庭助手 设计方案

> 状态：**v0.6**，已评审并修订。**v0.6 更换身份模型**：身份改由 Hermes profile（连接级）+ 每成员 token 提供，工具面不再有任何说话人身份参数；D10/D11/D12 退役（见 §12 与 §3.2）。评审记录：`docs/评审-v0.5-外部评审.md`。项目代号与目录名（`family-assistant`）均为占位，可随时改名。
> 日期：2026-10-04。本文档从零起稿，不参考任何既有方案。
> Hermes Agent 相关结论基于 2026-10-04 官方文档查证（见 §3 及文末来源）；v0.5 的复核同样基于 2026-10-04 官方文档原文。

## 0. 定位

一句话：**一个给 AI Agent 当后端的家庭事务程序**。

- 它本身没有对话能力，也不解析自然语言。它把待办、日程、记账做成一组结构清晰、语义明确的 MCP 工具，供 AI Agent 调用。
- 家人**在 QQ / 微信里和 Hermes Agent 说话**（家人已在用 Hermes），Hermes 负责理解意图并调用工具；程序负责事实——数据、校验、统计与回执话术。
- 部署在家庭自托管设备上（与 Hermes 同机），全家共享同一份数据。

三个功能域：**待办、日程、记账（轻量流水账，双账本）**，外加贯穿三域的**家庭成员**概念。

OQ 解答记录（2026-10-04，用户确认）：OQ2 归属人必须明确 → entry.member_id 必填、回执必标注；OQ3 → D8/D9（**D9 于 v0.4 修正：由"分视角不隐藏"改为"仅个人可见"**）；OQ4 成员微信和 QQ 都用（如 A 用 QQ、B 用微信）→ §3.3 按成员各自通道投递；OQ5 与 Hermes 同机 → D2。OQ6 于 v0.5 关闭（见 §3.3：微信侧群投递按不支持处理）。

由 D1+D2 派生的核心判断：**本方案最难的工程问题不是并发与同步，而是工具面的语义设计**——模型拿到工具后会不会用、用得对不对、错了能不能自己纠正。本文档的主要篇幅都给了这件事（§5、§8）。v0.5 追加的第二难点是**身份的正确性**：v0.5 用"配置层通道绑定"、v0.5.2 再加"凭据"，**v0.6 换成"身份来自连接"（D13）**——不再要求模型申报任何身份，是本轮最重要的修订。

### 0.1 威胁模型（v0.5.2 新增，先于一切权限讨论）

V1–V9 的强度完全取决于它假设的对手是谁。先写清楚，避免读者（包括未来的自己）高估这套机制。

| 对手 | 在模型内？ | 处置 |
|---|---|---|
| 家人本人（含互相打听安排） | ✅ | 一律按 V1–V9 拒绝；R7 的协商出口是本人把事项建成全家日程，而不是放开权限 |
| **模型自身犯错**（填错参数、误解意图、转录 id 出错） | ✅ | 主要威胁。靠 P2/P5/P8 + 写操作即时回执 + 软删兜底 |
| 已绑定通道内、**用户用话术诱导模型越权**（"用妈妈的身份查一下"） | ✅ | **结构性不可表达**（D13）：工具面没有说话人身份参数，模型想冒充也没有位置可填 |
| **输入内容不可信**（消息正文、待办标题、备注、日程名、Agent 读到的外部网页） | ✅ | 同上。提示注入能让模型做错事，但**改不了它是谁**；越权读写仍被 V1–V8 挡住 |
| **profile / token 配错**（把爸爸的 token 装进妈妈的 profile） | ✅ | 服务端比对"token 所属成员"与请求身份，不一致立即 `DENIED`（`identity_mismatch`）——**配错是响亮的失败，不是静默串号** |
| **群聊**（某个 bot 被拉进多人会话） | ✅ | 该会话里所有人的发言都会被当成 profile 主人。**对策：bot 不进群**（Hermes 侧群策略保持 disabled；微信 iLink 本来就不投递群事件，§3.3） |
| 局域网内的其他人 / 陌生人给 bot 发消息 | ❌ | 由 Hermes 侧 DM allowlist / pairing + `/mcp` 回环绑定挡在门外。**必须显式配置**（§3.1），程序侧不重复实现网络访问控制 |
| 拿到设备 root / 物理接触 | ❌ | 家庭自托管的前提，明确排除 |

**一句话**：这套权限的边界是"**防误用与防越权诱导，不防已经拿到凭据的人**"。v0.6 之后，"越权诱导"这一整类攻击**在结构上不可表达**——工具面里没有可以填别人名字的位置。

## 2. 总体架构

```
家人 A（自己的 QQ bot）──┐
家人 B（自己的微信 bot）──┤   每人一个 Hermes profile
家人 C（自己的 QQ bot）──┘   各自私聊，各自 family token
        │
        ▼
┌──────────────────────────────┐
│  Hermes profile：妈妈          │  ← 各自的 bot 凭据、技能、cron
│   mcp_servers.family:         │  ← D13：token 属于谁，身份就是谁
│     Authorization: Bearer …   │     提示词里没有任何身份信息
└───────────┬──────────────────┘
            │  MCP over HTTP（绑 127.0.0.1）+ 每成员 Bearer
            ▼
┌───────────────────────────────────────┐
│             家庭助手服务端（同机）        │
│   ┌────────────┐   ┌───────────────┐  │
│   │ MCP 工具面  │   │ 查看页 / 管理页 │  │  ← 同一进程两个 HTTP 门面
│   │ (127.0.0.1)│   │ (局域网网卡)    │  │
│   └──────┬─────┘   └───────┬───────┘  │
│          ▼                 ▼          │
│   ┌────────────────────────────────┐  │
│   │  领域层（待办 / 日程 / 记账）     │  │
│   └───────────────┬────────────────┘  │
│                   ▼                   │
│             SQLite（WAL）             │
└───────────────────────────────────────┘
        ▲
家人手机浏览器 ──局域网──┘（查看页，按成员登录）
```

- 单进程、单库、顺序写。并发写由 SQLite 事务保证，无需任何冲突处理机制。
- 同机部署（D2）：MCP 端口只绑回环地址，外部无法触及；查看页需要家人手机访问，绑局域网地址并按成员登录。
- **服务端无会话状态**：身份**逐请求**由 token 推出，服务端不保存任何"当前成员"。例外：查看页的浏览器会话——那是真人对真浏览器的绑定，不违反这一条。
- **身份在连接层解决**（D13）：每个 profile 用自己的 bot 凭据接自己的私聊，用自己的 token 连服务端。工具面里**没有说话人身份参数**——"我是谁"不是模型能填的东西，而是连接的属性。这与 v0.5 的"配置层通道绑定"差别很大：那条路把身份放进提示词，模型仍有表达的机会；这条路把它放进连接，模型连表达的位置都没有。

## 3. Hermes 集成

### 3.1 连接配置（每成员一个 profile，各带自己的 token）

每个成员在**自己的 Hermes profile** 里注册同一个 family MCP server，只差一个 token：

```yaml
# ~/.hermes/profiles/妈妈/config.yaml
mcp_servers:
  family:
    url: "http://127.0.0.1:8347/mcp"        # 同机回环地址（D2）
    headers:
      Authorization: "Bearer <妈妈 的 family token>"
      X-Family-Member: "m-261004-w9jn"      # 妈妈 的成员 id（声明头，**必填**，见下）
```

服务端由 token 反查成员（`api_token.member_id`），**身份就此确定，与请求体里的任何字段无关**。程序侧 `/mcp` 支持 Streamable HTTP；Hermes 支持 `headers`、超时、工具级 include/exclude（`lazy`、`timeout`、`tools` 等 key 可按需用）。

**身份声明头必须同时配置（2026-10-04 实测后收紧，`FA_REQUIRE_IDENTITY_HEADER` 默认 `true`）**：服务端除了 token，还需要连接**声明**自己属于谁，两者不一致才谈得上"响亮失败"；只配 token 时服务端没有任何第二个信息源，**配错就无法被发现**。实测过反面：把爸爸的 token 装进妈妈的 profile 且**漏写**声明头，请求会 0 报错地以爸爸身份运行（妈妈的 profile 原样返回爸爸的待办）——正是 S7 要求禁止的"静默串号"。因此**缺声明头一律 `DENIED(identity_mismatch)`**；置 `FA_REQUIRE_IDENTITY_HEADER=0` 可退回旧语义，仅供升级中的旧部署过渡，不推荐。声明头的值**必须是成员 id**（`m-…`）：HTTP 头只能放 ASCII，填中文成员名会在客户端 `fetch` 阶段就报错。管理端 `token generate` 会直接打印含该头的配置片段。

**为什么 token 要按成员分，而不是一个共享 token**：共享 token 下，任何能连上服务端的调用方都能"声称"自己是任意成员；按成员分之后 **token 与成员一一对应，配错立刻报 `identity_mismatch`**——这正是 R1 残余风险的处置方式：把"配置写错"从**静默串号**变成**响亮失败**。

**Hermes 侧访问控制（上线阻断项）**：程序只保证"拿这个 token 的人是谁"，**谁能跟 Agent 说话由 Hermes 决定**，必须显式配置、不得依赖默认值：

- **DM allowlist / pairing**：微信侧 `dm_policy` 的**平台默认值是 `open`**，而 gateway 安全章节写的是"默认拒绝未在 allowlist / 未配对用户"——两处表述层级不同，**不要依赖任何默认值**。显式设置 allowlist（`WEIXIN_ALLOWED_USERS` 等）或 pairing，逐个确认家人能进、外人进不来。
- **bot 不进群**：群聊里所有人的发言都会被当成该 profile 的主人（见 §0.1）。Hermes 侧群策略保持 `disabled`；微信 iLink 本来就不投递群事件（§3.3）。
- **收窄工具面**：家人通道的 Agent 只保留 family 工具集 + 必要的只读工具，避免提示注入借其它工具产生副作用。
- `/mcp` 只绑 127.0.0.1（D2）；token 由管理页**按成员**生成、可吊销。

### 3.2 身份传递（v0.6 重写）

**查证结论（官方文档原文）**

- `mcp_servers` 配置**按 profile 独立**，官方明确"credentials are never shared across profiles"。
- 官方把"**One agent per family member**"列为多 profile 部署的典型用法：每个 profile 有自己的 bot 凭据、会话、技能与 cron。
- 官方**没有**把消息通道发送者身份注入 **MCP 工具调用**的机制：`identity_header` 只有 `static` / `profile` 两种取值，都是**连接级静态值**（`profile` 在连接时解析一次）。
- cron 任务运行在**全新的 agent session**，且 job **归属某个 profile**（存在该 profile 自己的 home 下、随 profile 启停）。
- 另有一处细节值得记下：gateway 的 steer / 当前轮重定向会把 `platform, chat, thread, sender, message, profile, scope` 作为**模型可见**的 per-message JSON 上下文带进会话，官方同时明确它是 "routing data, **not authorization**"。本方案不把它作为授权依据；若日后要用作旁路交叉校验，注意 `privacy.redact_pii: true` 会把这些标识哈希掉。

**结论：身份放在连接上。**

1. **每成员一个 Hermes profile**（各自 bot 凭据、各自私聊）→ 每个成员的对话天然落在自己的 profile 里。
2. **每成员一个 family token**，写在该 profile 自己的 `mcp_servers.family.headers.Authorization` 里 → 服务端由 token 反查成员，**身份逐请求确定，不依赖请求体里的任何字段**。
3. **工具面没有任何说话人身份参数**：没有 `as_member`、没有 `bind_key`。

**由此得到的三条性质**

- **冒充在结构上不可表达。** v0.4 靠模型自觉、v0.5 靠照抄提示词、v0.5.2 靠 `bind_key` 校验；v0.6 让"声称自己是别人"这个动作**根本不存在**。提示注入能让模型做错事，但改不了它是谁。
- **配错会响亮失败。** token 与成员一一对应：把爸爸的 token 装进妈妈的 profile → `DENIED`（`identity_mismatch`），而不是静默以爸爸身份运行。这是 R1 残余风险的正面处置。
- **定时路径与对话路径同源。** cron job 属于某个 profile，运行时自然带着那个 profile 的 token——**D11 那条"prompt 里写死 `as_member` 字面值"的硬约束整个消失了**（R2 的定时路径风险随之关闭）。

**归属仍然是参数，说话人不是。** 这条区分是 v0.6 的关键，别混：

| | 是什么 | 从哪来 | 例子 |
|---|---|---|---|
| **说话人** | 身份 | **连接**（token） | 谁在说话——工具里**没有**这个参数 |
| `owner` / `member_id` | **归属目标** | 参数（合法业务参数） | "帮妈妈记一条"——记在谁名下 |

所以 V4（代记）仍然成立：爸爸调用 `add_todo(owner="妈妈", …)` 时，服务端知道**说话人是爸爸**（token）、**归属是妈妈**（参数），回执因此可以确定地写"仅 妈妈 可见，**由 爸爸 代记**"——比 v0.5 里靠模型自述的"由 你 代记"更硬。

**回执仍要标注归属与可见范围**（唯一用户能自己发现错误的防线）："已为 妈妈 添加待办……仅 妈妈 可见，**由 爸爸 代记**"。v0.6 之后这句话由服务端生成（说话人来自 token、归属来自参数），不再依赖模型自述。

**降级路径（V9 重写）**：v0.5 的"未绑定通道 → 反问 → 自报名字"整条路删除。v0.6 的规则是**没有有效 token 就没有身份**：未注册 / 未知 token → 一切工具 `DENIED`（`reason:"unknown_profile"`），**不回落到任何默认成员**。群聊不支持（bot 不进群，§3.1）。

**提示词资产的降级**：v0.5 的 `docs/hermes-system-prompt.md` 曾是"权限模型的 root of trust"，要求与配置逐字一致、diff 式 review。v0.6 起它降级为 **`docs/hermes-skill.md`**——一份纯工具语义 + 说话纪律的 Hermes skill，**按 profile 各装一份、内容完全相同、里面没有任何身份信息**。它不再承载权限，因此可以随时改，也不需要与配置 diff。

**已评估并否决**的替代方案：

- 服务端记录"当前成员"——会话状态，并发串号。
- 由 Agent 从"通道用户名"自由推断身份——v0.4 方案。
- **`channel_overrides.<chat_id>.system_prompt` 注入身份（v0.5 的方案，v0.6 否决）**——它把身份放进**提示词**，本质上仍要求模型逐轮照抄；而该 key 是**替换**而非追加全局 prompt，会接管成员在该会话里的整个人格（评审 P1-4）；还要额外维护一份必须与配置逐字一致的提示词资产。收益（把错误率从"每轮"降到"配置一次"）远不如"让身份不可表达"。
- `identity_header: profile`——它确实能给出 profile 名，但**单连接下所有成员共用一条连接**，这个值恒等于同一个 profile，只有在"每成员一个 profile"（也就是本方案）的前提下才有意义。v0.6 用 per-profile 配置 + 每成员 token，不需要它。

### 3.3 提醒与摘要推送（Hermes cron，程序零推送代码）

Hermes 内置 cron 调度器：自然语言或 CLI 建任务，每个任务指定 `deliver` 投递目标（`weixin`、`qqbot`、按 id 指定具体会话，支持逗号分隔多目标）。成员通道各异（OQ4：A 用 QQ、B 用微信……），故**每个成员各自的摘要任务投递到各自通道**：

| 任务 | 节奏 | 程序侧被调工具 | 投递 |
|------|------|----------------|------|
| 个人今日摘要 × 每 profile | 每天 08:00 | `get_today()`（**无身份参数**，身份随 profile） | 本人私聊 |
| 个人催办 × 每 profile | 每天 18:00 | `get_today()`（逾期部分） | 本人私聊 |
| 记账周报 | 每周日 20:00 | `summarize_entries`（上周，共享账本） | 逐人私聊（v0.5 结论，见下） |

**~~D11~~（v0.6 退役）**：v0.5 曾要求"每个 cron 任务的 prompt 里 `as_member` 必须写死字面值"。v0.6 之后这条不再需要——**cron job 归属某个 profile，运行时自然带该 profile 的 token，身份自动确定**（§3.2）。于是：

```
GOOD: 调 get_today，看今天有什么。（不用传任何身份参数）
BAD:  调 get_today，as_member 传"当前用户"。（这个参数已经不存在了）
```

**每个成员一份 cron 配置**（存在各自 profile 的 `cron/jobs.json` 下），投递到各自私聊。R2 的定时路径风险由此关闭——不再有"prompt 里的身份字面量被写错或被模型改掉"这个类别。

**OQ6 关闭（v0.5）**：微信侧群投递按**不支持**处理。官方文档明确：微信适配器 QR 登录连的是 iLink **bot 身份**，普通微信群事件通常根本不投递给该身份，`WEIXIN_GROUP_POLICY` 对此类账号基本无效。QQ 群若日后确认可用可另行加投递，但设计不依赖它——周报与提醒一律逐人私聊。配置与投递目标属 Hermes 侧资产；程序只保证被调工具返回适合直接转发的话术（P3）。个人摘要里只含本人待办与全家日程（V1/V2 保证）。

**cron 侧的两条实现要求（v0.5.2 新增，官方查证）**：

1. **必须点名 family 工具集**：cron agent 拿的是 `cron` 平台配置的工具集（`hermes tools` 里的 cron 平台，或 job 自己的 `enabled_toolsets`），**不是 CLI 默认值**。漏配会导致定时任务根本看不到 family 工具。好在 cron 的 preflight 会把它判为 `blocked_config` 并**只告警一次**、不花 token——所以不会静默失败，但必须进上线检查项。
2. **投递目标写具体**：`deliver` 支持 `platform:chat_id[:thread_id]` 形式与逗号分隔的多目标。注意：**一个 job 的内容对所有收件人相同**，而身份随 profile 确定，所以**带个人数据的摘要必须每人一个 job**；只有共享账本周报可以一个 job 多目标。

**v0.7 评估项：把推送路径改成 `no_agent`（v0.6 起降级为可选优化）**：cron 支持 `no_agent` 模式——脚本 stdout 原样投递、**零 LLM 参与**。若程序额外提供一条只读 CLI（复用 domain 层与 P3 话术），周报与个人摘要可改为"脚本 + `deliver`"：不花 token、不可能算错数字。**注意它最初的理由已经消失**——v0.6 的身份来自 profile，D11 那条"prompt 里写错身份"的风险类别本就不存在了，所以这条现在纯粹是省钱与确定性优化。代价是 D1"只做 MCP 服务端"要松一格（多一条只读出口，必须复用同一套可见性过滤层）。登记为 v0.7 评估。

## 4. 领域模型

三域统一约定（一套模式贯穿，模型学一次就会用全部）：

- **主键 `id`（v0.5 改）**：`<域前缀>-<yymmdd>-<4位随机>`，如 `t-261004-a7k3`（待办）/ `e-260415-m2x9`（日程）/ `n-261004-q8w1`（流水）。v0.4 用 8 位纯随机串，与 P5（删除必须精确传 id、Agent 必须先 list 取 id）冲突：随机串要经模型转录，字符混淆（`0`/`O`、`1`/`l`/`b`）错误率不低，一次转录错误就是一次失败删除或误删。改为**时间序前缀**后，前缀防跨域混淆、日期段便于人工排查、随机段缩短到 4 位以降低转录量。**唯一性由 DB UNIQUE 约束保证**（同域同日冲突时重新生成），不依赖 4 位随机段的概率（v0.5.2 补）。
  - 配套输出纪律：所有 list 结果中，id 必须与序号、标题同行出现（如 `1. [t-261004-a7k3] 交物业费`），回执同时回显 id，让用户能直接说"删第 3 条"而无需复述 id。
- 软删除：`deleted_at` 非空即视为已删；`restore_deleted` 可恢复；所有 list 默认排除已删。
- 时间：家庭固定单时区（服务端**显式配置**，默认 Asia/Shanghai）。日期时间用 `YYYY-MM-DD HH:MM`，纯日期用 `YYYY-MM-DD`。**实现不得依赖系统本地时区**（v0.5.2 补）：容器默认 UTC 会让"今天""本周"整体偏移一天，`get_today`、cron 摘要、`occurred_date` 默认值全部受影响。
- 金额：整数"分"。

### member

```
id, name, aliases[]          → 家庭称呼，如 ["妈妈","老妈","王丽"]；用于 owner / member_id 的归属解析（v0.6：不再用于身份匹配）
web_password_hash            → 查看页按成员登录（§6）
created_at, deleted_at?
```

身份凭据不在这张表里——它在 `api_token.member_id`（见下）。

- **成员删除（v0.5.2 补）**：成员一律**软删**（`deleted_at`）。名下数据保留，读取时显示"已移除成员"，历史回执仍可解释。硬删需先处理关联数据（外键 RESTRICT），不作为常规操作。软删后查看页登录与**该成员的 token** 一并失效。

### api_token（v0.6 起按成员）

```
id, member_id, label, token_hash, created_at, revoked_at?
```

- `member_id` 就是身份来源（D13）：服务端由 token 反查成员，**这是"谁在说话"的唯一依据**。
- 每人一条（或每人多条便于轮换）；吊销某人的 token 不影响其他人。
- 管理页生成时明文只显示一次，只存 hash（token 用足够熵的随机串）。

### todo（待办）

```
id, owner_id        → 归属成员，必填；待办一律个人项（D9）
title, notes?
due_date?           → 纯日期，可空
done, done_at?
created_by, created_at, deleted_at?
```

无优先级字段（刻意不做，见 N7 与路线图）。

### event（日程）= 系列 + 实例

```
event_series:   id, owner_id?（空 = 全家共享；指定 = 个人日程）, title, location?, notes?,
                repeat(none | daily | weekly | monthly), repeat_interval, repeat_until?,
                created_by, created_at, deleted_at?

event_instance: id, series_id?, owner_id?, title, location?, notes?,
                start, end?, all_day, created_by, created_at, deleted_at?
```

- `repeat ≠ none` 时**写时物化**：创建/修改系列即预生成未来 92 天的实例，读取越过边界时惰性续期。
- **惰性续期的失败语义（v0.5 补）**：续期是写在读路径上的写操作。磁盘满、锁竞争、迁移异常都可能在读日历时被触发。规定：续期在读事务内 `try/catch`，失败时**降级返回**——照常返回已物化范围内的实例，并在 `message` 中明确说明"日程只展开到 X，之后的重复日程需稍后重试"。**读操作绝不因为续期失败而整体报错**：家人的日历查询不能被一次后台写失败整体拖垮。
- 对重复日程的修改/删除只作用于**整系列**（单次实例修改见 N4）。
- `all_day` 事件的 start/end 为纯日期。

### entry（记账流水）+ category

```
entry:    id, type(expense | income), amount_fen(>0 整数), category_id?,
          ledger(shared | personal),
          member_id        → 归属人（这笔算谁的），必填（OQ2：必须明确）
          note?, occurred_date(YYYY-MM-DD，默认今天),
          created_by, created_at, deleted_at?

category: id, name, kind(expense | income), sort_order
```

- 预置支出分类：餐饮、交通、购物、居住、娱乐、医疗、教育、人情、其他；收入：工资、理财、红包、其他。
- **category 可缺省**：允许记"未分类"，汇总中单列。不强制每次分类，降低对话摩擦。
- `occurred_date` 只到日——家庭记账的时间粒度。
- **一致性校验（v0.5.2 补）**：`category.kind` 必须与 `entry.type` 一致（收入分类不能记在支出上），不一致返回 `INVALID_PARAMS` + 话术；`category_id` 不存在返回 `NOT_FOUND`。
- **金额异常提示（v0.5.2 补）**：单笔金额 ≥ 配置阈值（默认 ¥10,000）时，回执 message 追加一句确认提示。**不硬拒**——家庭可能真有大额支出，硬拒会挡住合法场景；但静默接受会让"35 元"误录成"35000 元"无从察觉。

### 可见性不变量（领域层强制，工具层不可绕过）

统一覆盖三域（v0.4 起取代原 I1–I4）：

- **V1 个人项仅本人可见**：todo（一律个人项，owner_id）；owner_id 非空的 event；ledger=personal 的 entry（归属 member_id）。
- **V2 共享项全员可见**：owner_id 为空的 event（全家日程）；ledger=shared 的 entry（member_id 即共享账本中的归属人）。
- **V3 个人项仅本人可改删**（update/delete/complete/reopen/restore）；共享项家庭内互信，任何成员可纠错（回执标注操作者）。
- **V4 代他人写入允许，但边界不同**：`add_todo` / `add_event` 可指定 `owner` ≠ 说话人（回执标注"仅 TA 可见，由 <说话人> 代记"——**说话人由连接确定，不是模型说的**）；entry 例外——`ledger=personal` 只能本人写，`ledger=shared` 可代记并指定归属人。
- **V5 读取一律过滤 + 显式越权返回 DENIED**：一切 list/get/summarize 输出排除调用者不可见项；当请求**显式**指向他人个人数据（如 owner=他人 的待办查询、ledger=personal 且 member ≠ 说话人）时返回 `DENIED` 而非静默空表——静默空表会让 Agent 误报"TA 没有待办/没花钱"。
- **V6 权限与读取同源**：个人项的 id 只出现在本人可见的读取结果中，因此"先 list 后改删"（P5）天然带权限校验；跨成员传他人条目 id 的改删请求按 V3 拒绝。
- **V7 归属与账本创建后不可变（v0.5.1 新增；v0.5.2 细化拒绝语义）**：`entry.ledger`、`entry.member_id`、`todo.owner_id`、`event_series.owner_id`、`event_instance.owner_id` 一经写入，**不得改变**。`update_todo` / `update_event` / `update_entry` 的 schema **保留**这些字段（模型做"读-改-写"时需要原样回传），但：传入值与现值**相同** → 幂等放行；传入值与现值**不同** → `DENIED` + `reason:"immutable"` + 固定话术"归属/账本不可修改，如需变更请删除后重建"。跨账本、跨归属的迁移一律走"软删 + 重建"，重建时按新状态重新过 V3/V4。
  - 为什么 schema 保留字段而不是删掉它（v0.5.2 修正 v0.5.1 的写法）：字段不存在时，模型只会拿到一个语焉不详的校验错误、然后换个参数重试；字段存在 + 明确的拒绝话术，才能让模型一次就知道"这条路不通"。这也正是 P8"description 显式写出拒绝条件"的用法——三条 `update_*` 的 description 必须写明这条。
  - 理由：V1–V6 判定的是**行的当前状态**，而 update 恰恰能改变状态本身。没有 V7，以下四条都是"合法"的：把共享流水改成个人流水（隐藏公共支出）、把个人流水改成共享（泄露私账）、把全家日程改成某人的个人日程（全家事项被单人藏起来）、把我的待办改成别人的（归属漂移，被改的人还不一定能发现）。V7 是把"权限判定"与"被判定字段"解耦的补丁。
- **V8 创建者对自己代记的条目保留可见与删除权（v0.5.2 新增）**：对"**我创建、归属他人**"的个人项（todo、个人日程；个人账本 entry 因 V4 已禁止代记而不涉及），创建者拥有**查看权**与**删除权（软删）**，**不含修改权**——修改会在不通知归属人的情况下改变 TA 看到的内容。删除时回执标注"已撤回你代记的条目"。**v0.6 起 `created_by` 就是连接身份**（D13），不可伪造、也不来自参数。
  - 理由：V4 允许代记，但 v0.5.1 之前"我帮妈妈记的待办"创建者既看不见也改不了，写错了只能求妈妈自己删。创建者本就输入过这条内容，给他可见权**不增加任何隐私暴露**，却消掉一个必然被家人抱怨的坑。
- **V9 没有有效 token 就没有身份（v0.6 重写）**：请求未携带**已注册且未吊销**的 token 时，一切工具返回 `DENIED`（`reason:"unknown_profile"`）——**不回落到任何默认成员**。
  - 理由：v0.5.2 之所以需要"匿名只读共享"，是因为身份可能"不可知"；v0.6 之后身份**要么确定、要么不存在**，没有中间态。群聊那个场景改由"bot 不进群"（§3.1）在产品层解决，不需要在权限层开一个口子。

### 可见性真值表（v0.5 新增，v0.5.1 纳入 V7，v0.5.2 纳入 V8/V9，V1–V9 的可执行形式）

散文描述会被实现者各自解释，权限 bug 又几乎全部藏在**反例**里。因此把 V1–V9 展开成三张按域枚举的表，作为实现与测试的唯一对照。角色：本人 = **连接身份**指向的那位；他人 = 任意其他成员。

**读表前先记住 V7**：三张表只回答"按行的**当前状态**能不能操作"，不回答"这次操作会不会改变判定所依据的字段"。跨列迁移（改 owner / 改 ledger）不是本表的空档，而是**一律禁止**——表中 update 行的 ✅ 均以"被判定字段不变"为前提。

**两条横向补充**：① **V8**——在"目标 owner = 他人"列中，若调用者正是该条目的 `created_by`，则 list / get / delete 为 ✅、update / complete 仍为 ❌；② **V9**——无有效 token 的调用**整表皆 `DENIED`**（不存在"低权限成员"这种状态）。

### 反例清单（v0.5 新增，v0.5.1 扩至 X14，v0.5.2 扩至 X16）

|---|---|---|---|

| X8 | C：`update_event(全家日程)` | ✅ **必须放行**，回执标注操作者 | V3 互信是刻意设计，不是漏洞 |
| X9 | 未知 / 已吊销的 token 调用 `get_today()` | `DENIED`（`reason:"unknown_profile"`），**不回落默认成员**（V9） | 静默当作某个人，就是一次身份事故 |
| X10 | 爸爸：`add_todo(owner="妈")`（归属目标匹配不到 / 重名） | `MISSING_PARAMS` + 成员名单 / `AMBIGUOUS` + 候选 | 归属写错人：条目落到错误的成员名下，且只有 TA 看得见 |
| X11 | A：`update_event(全家日程, owner=A)`（把全家日程改成自己的个人日程） | `DENIED`"归属不可修改"（V7）；如需改归属须删除后重建 | 全家事项被单人藏进私档，且没有任何操作痕迹 |
| X12 | A：`update_entry(A 的个人流水, ledger=shared)`（把私账改成共享） | `DENIED`（V7） | **隐私泄露**：一句话把自己的私账发布给全家（模型把"记成共享的"误解成"改成共享的"时尤其容易触发） |
| X13 | B：`update_entry(共享流水, ledger=personal, member_id=B)`（把公共支出挪进个人账本） | `DENIED`（V7） | 公共资金流向被单人改写，汇总与对账全部失真 |
| X14 | A：`update_todo(A 的待办, owner=B)`（把自己的待办甩给别人） | `DENIED`（V7） | 归属漂移：B 凭空多出一条自己没写过的待办，而 A 已看不见它、无法自查 |
| X15 | 妈妈：`list_todos(as_member="爸爸")`（模型被诱导去传一个不存在的身份参数） | `INVALID_PARAMS`（未知字段）——**说话人不是参数**（D13） | 只要存在"说话人参数"，提示注入就有一条路可走；v0.6 里它不存在 |
| X16 | A 的待办由 B 代记：B 查看/删除它；C 查看它 | B ✅ 可见、✅ 可删、❌ 不可改（V8）；C 一律 ❌ | 假阴性会让代记者无法纠正自己的笔误；假阳性则让 V8 变成一条旁路 |

**实现约束**：`DENIED` / `MISSING_PARAMS` / `AMBIGUOUS` / `INVALID_PARAMS` / `NOT_FOUND` 响应必须自带**可直接转述的中文话术**（P3），否则模型会自己编一个理由，错误信息就不可控了。V7 的 `DENIED` 尤其要说清"**请删除后重建**"——只回一句"不允许"会让模型换个参数反复重试（`docs/hermes-skill.md` §1 已明令不得绕过拒绝，但话术仍要给出出路）。

## 5. MCP 工具面

工具面是本程序的产品本体。八条设计原则：

- **P1 参数即语义**：枚举、ISO 日期、整数分。程序不解析自由文本；把"35 块"换算成 3500 分是 Agent 的活。
- **P2 不猜**：参数缺失或非法时返回结构化澄清请求（**码表与信封见 §5.1**）——`MISSING_PARAMS`、`INVALID_PARAMS`、`AMBIGUOUS`（归属目标重名，附候选）、`DENIED`（越权/不可为，带 `reason`）、`NOT_FOUND`。把"澄清"变成协议，而不是事故。默认值仅限显然项（如 occurred_date 默认今天）。
- **P3 返回即话术**：所有写操作返回完整 record + 一句可直接转述/转发的中文 message，Agent 无需再组装事实。
- **P4 数学在程序做**：一切统计、汇总、合计走工具，禁止让模型心算流水。
- **P5 危险操作显式化**：删除必须携带精确 id（Agent 必须先 list 拿到 id），返回被删记录；一律软删、可恢复。程序永远不接受模糊删除。
- **P6 小工具不复用**：不用 mode 参数把多个操作塞进一个工具；每个工具语义单一、参数面小。**唯一例外（v0.5.2 明确）**：`restore_deleted(kind, id)`——恢复在三个域上语义完全同构且极低频，拆成三个工具只会膨胀工具面。此例外经评审确认，不再是遗漏。
- **P7 身份在连接里、服务端无状态**：说话人由请求携带的 token 决定（D13），**工具面没有任何说话人身份参数**；涉及归属的仍传 `owner` / `member_id`——那是"记在谁名下"，不是"我是谁"。服务端不保存任何跨请求身份状态：身份逐请求由 token 推出。
- **P8 描述即契约**（v0.5 新增）：工具的 `description` 就是模型的行为契约，模型的权重远高于本文档，因此 description 本身受本方案约束——① **用中文写**（系统提示与用户输入均为中文，英文描述会引入一层翻译损耗）；② 每条 description 内**显式写出拒绝条件**（如"个人账本仅本人可写：`ledger=personal` 时 `member_id` 必须等于说话人，否则返回 DENIED"），因为 V1–V9 的约束若只存在于设计文档，模型读不到；③ 给出 1 个正确调用示例；④ **不可变字段的拒绝条件也要写明**（v0.5.2）：三条 `update_*` 必须包含"归属/账本不可修改，如需变更请删除后重建"（V7）。description 变更与 schema 变更同等对待，走 golden 测试。

### 工具清单（20 个；v0.5.2 重新核对计数）

| 域 | 工具 |
|----|------|
| 通用（2） | `list_members` / `get_today` |
| 待办（6） | `add_todo` / `list_todos` / `update_todo` / `complete_todo` / `reopen_todo` / `delete_todo` |
| 日程（4） | `add_event` / `list_events` / `update_event` / `delete_event` |
| 记账（5） | `add_entry` / `update_entry` / `list_entries` / `summarize_entries` / `delete_entry` |
| 分类与恢复（3） | `list_categories` / `add_category` / `restore_deleted` |

关键签名说明（完整 schema 实现时定；**v0.6 起所有工具都没有说话人身份参数**——说话人来自连接，下文不再逐条重复）：

- `list_members()` → 返回 name + aliases，**供模型把"我妈"这类说法映射成 `owner` / `member_id`**（v0.6：它不再服务于身份解析——身份来自连接）。**v0.7 计划**：同时返回各成员是否有可用 token（程序侧可知的那一半；profile 侧配错由 `identity_mismatch` 报错兜住）。
- `get_today()` → 本人今日待办（到期 + 逾期未完成）+ 今日全家日程。**无参数**（说话人来自连接）。两个用途：Agent 每轮对话开场拉取；Hermes cron 个人摘要的数据源（§3.3）。
- `add_todo(owner, title, due_date?, notes?)` → `owner` 缺省 = 本人；可为他人（V4 代记），回执标注可见性与说话人。
- `list_todos(done?, due_before?, due_after?, q?)` → **无 owner 参数**：只返回说话人本人的待办（V1）；查他人待办的需求被模型层直接取消。
- `complete_todo` / `reopen_todo` / `update_todo` / `delete_todo`（id, …）→ 仅限本人待办（V3/V6）；`owner` **不可改**（V7：传入不同值 → `DENIED` + `reason:"immutable"`，同值幂等放行）；`update_todo` 不接受 `done`（`done` 只走 `complete_todo` / `reopen_todo`，避免两条路径产生不一致的话术）。
- `add_event(owner?, title, start, …)` → owner 缺省 = 全家日程；owner=他人 = 为 TA 代记个人日程（V4）。
- `list_events(start, end, scope?(family|mine))` → scope 缺省 = 全家日程 + 本人个人日程；`scope=mine` 仅本人个人日程；**没有"看他人个人日程"的参数形态**（V1）。
- `update_event` / `delete_event`（id, …）→ 个人日程仅本人，全家日程任何成员（V3）；`owner` **不可改**（V7：跨归属变更须删除后重建）。
- `add_entry(member_id, ledger, type, amount_fen, …)` → `ledger` 缺省为 `shared`，个人账本必须显式说且回执标注；ledger=personal 时 `member_id` 必须 = 说话人（V4）。
- `update_entry`（id, …）→ 仅限可见范围内的条目（V3：个人账本仅本人，共享账本任何成员可纠错）；`ledger` 与 `member_id` **不可改**（V7：传入不同值 → `DENIED` + `reason:"immutable"`）——跨账本迁移必须走 `delete_entry` + `add_entry`，否则"把自己的私账改成共享"会变成一条自泄露路径（X12）。
- `list_entries(start?, end?, member_id?, category_id?, type?, ledger?, q?)` → 可见性按 V1/V2/V5 过滤；`ledger` 缺省 = 全部可见范围（共享 + 本人个人）。
- `summarize_entries(period 或 start/end, group_by(category|member|ledger), type?, category_id?, member_id?, ledger?)` → 总额 + 分组明细；默认范围下输出按 共享/个人(本人) 分列，避免混算。**歧义消除（v0.5）**：`group_by=member` 而 `ledger` 缺省时，二维分组（共享按人 / 个人按本人）语义不唯一，模型极易自由发挥——此时一律返回 `MISSING_PARAMS`，要求显式指定 `ledger`；只有 `group_by=ledger` 时 `ledger` 才可缺省（此时本就是按账本分组）。
- `restore_deleted(kind, id)` → 恢复同样受 V3 约束。

> 相比 v0.1 删除了 `whoami`：连接层无成员身份可查（§3.2），该工具失去语义。

### 5.1 契约冻结（v0.5.2 新增）

§5 的八条原则若无具体形状，实现者必然分叉，而**分叉点恰好是 P8 认为最贵的地方**。以下先冻结；各工具的完整 schema 与 description 按同一模板逐个补齐，**Spike 01 的 4 个工具必须先补齐**。

**① 响应信封**（所有工具一致）

```json
// 成功
{ "ok": true,  "data": { …完整 record 或列表… }, "message": "可直接转述的中文话术" }

// 失败（不抛裸异常、不返回无话术的错误）
{ "ok": false, "code": "DENIED", "reason": "immutable", "message": "……", "hint": "……",
  "missing": ["title"], "candidates": [{ "name": "妈妈", "aliases": ["老妈"] }] }
```

`message` 永远是**可直接说给家人听的中文**（P3）；`hint` 是给模型看的下一步建议；失败时不存在 `data`。

**② 错误码表（冻结）**

| code | 含义 | 附带字段 |
|---|---|---|
| `MISSING_PARAMS` | 必填参数缺失 | `missing[]`、`hint` |
| `INVALID_PARAMS` | 参数非法：未知字段、类型错误、枚举非法、金额非正、`category.kind` 与 `type` 不符 | `field`、`hint` |
| `AMBIGUOUS` | **归属目标**（`owner` / `member_id`）匹配到多个成员 | `candidates[]` |
| `DENIED` | 无权或不可为，**必须带 `reason`** | `reason` ∈ `not_visible` / `not_writable` / `immutable` / `unknown_profile` / `identity_mismatch` |
| `NOT_FOUND` | id 不存在或已永久删除 | `id` |

分层规则：**结构问题**（未知字段、类型、枚举）→ `INVALID_PARAMS`；**语义问题**（越权、不可变）→ `DENIED` + `reason`。这条分界让 X1（未知字段）与 X11–X14（不可变字段）各自落在正确的码上，模型也才能分辨"换个参数重试"与"这条路根本不通"。另有**两类身份失败**独立于参数：未知/已吊销 token → `DENIED(unknown_profile)`；token 与请求身份不一致 → `DENIED(identity_mismatch)`（§3.2）。

**③ update 的置空语义**：字段**缺省 = 不改**；显式传 `null` = **清空**（如 `update_todo(id, due_date=null)` 表示去掉截止日期）；列表类参数传 `[]` = 清空。此约定必须写进每条 `update_*` 的 description，否则模型无法表达"把备注删掉"。

**④ 校验规则汇总**：`amount_fen` 为正整数（超异常阈值 → 回执追加确认提示，不硬拒）；`category.kind` 与 `entry.type` 一致；`occurred_date` / `start` / `end` 为合法日期且 `end ≥ start`；**token → 成员**的解析在 domain 层入口统一做一次（§3.2）；`owner` / `member_id` 按 member 表解析（匹配不到 → `MISSING_PARAMS` + 成员名单，重名 → `AMBIGUOUS` + 候选）。

**⑤ 模板（以 `add_todo` 为例，其余按此形状补齐）**

```ts
// schema：字段名与 P1 一致；description 用中文，内嵌拒绝条件与一个正确示例（P8）
add_todo({
  owner?: string,      // 归属人，缺省 = 本人；可为他人（代记，条目仅 TA 可见）
  title: string,
  due_date?: string,   // YYYY-MM-DD
  notes?: string,
})

// description（示意，实现时逐字定稿并进 golden 测试）
// 「添加一条待办。owner 缺省为本人；指定他人即代记，条目仅对方可见，回执会注明
//   "由你代记"。示例：add_todo(owner="妈妈", title="交物业费", due_date="2026-10-05")。
//   注意：说话人由连接确定，本工具没有、也不接受任何身份参数。」
```

## 6. 查看页与管理页

**查看页**（家人手机浏览器访问，**按成员登录**：选成员名 + 个人密码；会话 cookie）：

- `/todos`：**仅本人待办**（V1，无全家切换）。
- `/calendar`：全家日程 + 本人个人日程（他人个人日程不可见）。
- `/ledger`：**共享账本**（全员可见）+ **我的个人账本**（仅登录者本人，切换查看）；月度流水、分类汇总、按归属人筛选。他人个人账本不可见、不可切换（与 Agent 侧不同，这里是登录即真人）。

**管理页**（`ADMIN_PASSWORD` 保护，日常不碰）：

- 端点 token 管理：生成/吊销（供 Hermes 使用，不分成员）。
- 成员管理：增删成员（软删，见 §4）、维护 name/aliases、重置查看页密码、**按成员生成/吊销 family token（D13）**——明文只在生成时显示一次，服务端只存 hash；生成后要写进该成员 profile 的 `mcp_servers.family.headers`，配错会在下一次调用时报 `identity_mismatch`。
- 分类管理。
- **审计日志（v0.5.2 新增）**：最近 N 条写操作（时间 / **说话人** / 工具 / 关键参数 / 结果码）。这是 R1（配置写错）与 R6（脏数据）最便宜的兜底——回执只能让当事人当场发现，审计让事后追溯成为可能。只记元数据与关键字段，不记全文，避免把私账内容再复制一份。
- 数据备份：SQLite 在线备份下载（用 `VACUUM INTO` 或 backup API，**不要直接拷贝 WAL 模式下的库文件**）。
- 健康状态：MCP 端点、DB、最近备份时间、cron 最近一次投递结果（只读展示，程序不推送）。

**查看页与管理页的加固（v0.5.2 新增）**：① 口令一律哈希存储（`web_password_hash`；`ADMIN_PASSWORD` 用 scrypt/argon2 存哈希），**不得存在默认口令**，首次启动强制设置；② 登录失败限速与锁定；③ 页面仅绑局域网网卡（D2），并**明确承认局域网内无 HTTPS、口令以明文经过 Wi-Fi**——这是家庭自托管的已知代价，写进 §10 而不是假装不存在；④ 查看页的可见性过滤必须与 MCP 侧**共用同一个过滤层**（传入统一的 viewer 上下文 `{member_id, source: mcp|web}`，见 §9），不得在 web 层重写一遍 V1–V9。

## 7. 非目标（明确不做）

- **N1** 细粒度权限——V1–V9 之外不再细分（如字段级权限、按人的共享账本可见性）。
- **N2** 预算、账户、转账、复式记账（D4）。
- **N3** 程序内置推送通道——推送由 Hermes cron 承担（D7），程序只提供被调工具。
- **N4** 重复日程的单次实例修改（只整系列操作）。
- **N5** 多时区 / DST（单时区家庭）。
- **N6** 数据导入导出（路线图：JSON 全量导出）。
- **N7** 待办优先级、标签。
- **N8** 待办的"全家/共享"形态——待办一律个人项（D9）；家庭性事务用全家日程或逐人待办表达。

## 8. 关键流程走查

验证工具面能否闭环家人的真实说法：

1. **「午饭花了 35」**（微信，妈妈说的）→ `add_entry(member_id=妈妈, ledger=shared 缺省, type=expense, amount_fen=3500)` → 回执"已记入**共享账本**：10-04 支出 ¥35.00 · 未分类 · 归属：妈妈"。说"记我私账"→ `ledger=personal`，回执标注"已记入**你的个人账本**"。（**说话人不在参数里**——它由妈妈那个 profile 的 token 确定。）
2. **「这个月买菜花了多少」** → `summarize_entries(本月, group_by=category)`。若没有"买菜"分类：Agent 可建议 `add_category` 建好后补记，或用 `q` 关键词 `list_entries` 人工核对——不做按备注的模糊汇总，此为已知限制。
3. **「我们家这个月一共花了多少」** → `summarize_entries(ledger=shared, group_by=member)` → 共享账本总额 + 按归属人分列（V2 保证不含任何人的个人账本）。
4. **「每周三晚上七点游泳，记到年底」** → `add_event(owner=说话人, repeat=weekly, repeat_until=12-31)` → 个人日程（仅本人可见）；若说"全家…"则 owner 缺省为全家日程 → 物化约 13 个实例，回执列出首次时间并标注可见范围。
5. **「帮妈妈记一下，她明天要交物业费」** → `list_members` 拿成员 → `add_todo(owner=妈妈, due_date=明天)` → 回执"已为 妈妈 添加待办：交物业费（明天）——仅 妈妈 可见，**由 爸爸 代记**"（V4；说话人来自连接，回执里这个名字是服务端写的，不是模型说的）。
6. **「把上周五那笔奶茶删了」** → `list_entries(上周五)` → 唯一命中则 `delete_entry(id)`；多条则 Agent 列出让用户选。程序侧永远要求精确 id（P5）。
7. **隐私拒绝（三连）**：
   - B 问「看看 A 的个人账本」→ `list_entries(member_id=A, ledger=personal)` → `DENIED`："个人账本仅本人可见"。
   - B 问「A 有什么待办」→ `list_todos` 无此参数形态，Agent 直接说明"家人之间的待办互相不可见"；若 Agent 试图传 owner → `INVALID_PARAMS`（未知字段）。
   - B 问「A 周三有什么安排」→ `list_events` 返回中不含 A 的个人日程；B 显式要求时 → `DENIED`："个人日程仅本人可见"。
   - 三种情形 Agent 都原样转述原因，绝不静默返回空表。
8. **开场提醒** → Agent 每轮先 `get_today()` → "你今天 2 件事：15:00 牙医（全家日程）；另有逾期待办：交电费（10-01）"。
9. **每日 08:00 个人摘要**（Hermes cron 触发，无人在场）→ **该 job 属于妈妈的 profile，运行时自带妈妈的 token** → `get_today()`（无参数）→ Hermes 投递到妈妈私聊："今日 3 件事：……；逾期 1 条：交电费（10-01）"。程序无任何推送代码（D7），**prompt 里也不需要写任何身份**（D11 退役）。
10. **群聊里的请求**（v0.6 重写）→ **不支持**：bot 不进群（§3.1），微信 iLink 本来也不投递群事件（§3.3）。若某个 bot 被误拉进群，那个群里所有人的发言都会被当成该 profile 的主人——这是 §0.1 明确列出的边界，靠"不进群"这条运维纪律关闭，而不是靠在权限层猜身份。

## 9. 技术选型与工程结构

- Node 22 + TypeScript（MCP SDK 与查看页同一语言，类型贯通）。
- `better-sqlite3`（同步 API，事务模型简单）。
- `@modelcontextprotocol/sdk`（Streamable HTTP）。
- Fastify 承载 `/mcp`（127.0.0.1）+ 查看页/管理页（局域网网卡）。
- `zod` 做参数校验，校验错误直接映射到 P2 的结构化协议。
- 查看页用服务端模板字符串渲染，不引前端框架。

```
src/
  db/        schema、migration
  domain/    todos / events / ledger / members / categories / today（可见性 V1–V9 收敛在统一过滤层）
  audit/     写操作审计（v0.5.2 新增，append-only）
  mcp/       server、tools/*（薄壳，转调 domain）
  web/       views、admin、auth（成员登录 + 会话；复用 domain 的 viewer 过滤层）
  config.ts
test/        每工具集成测试 + 工具 schema golden 测试 + V1–V9 可见性专项测试 + X1–X16 反例逐条
```

分层纪律：**工具层薄、领域层厚**。工具只做参数转换与话术拼装，业务规则（含可见性不变量）全在 domain 层，可脱离 MCP 直接测试。**token → 成员**的解析也在 domain 层入口统一做一次（§3.2），不在每个工具里重复实现；工具层因此完全看不到"身份"这个概念。

## 10. 风险与开放问题

**风险**

- **R1**（v0.6 重写）身份错误：
  - ~~模型填错 / 被诱导填错说话人~~ —— **v0.6 结构性消除**（D13）：工具面没有说话人身份参数，模型想冒充也没有位置可填（X15）。
  - ~~用户自报身份直通~~ —— **v0.6 结构性消除**：不存在"自报"这个动作。
  - **profile / token 配错**（把爸爸的 token 装进妈妈的 profile）—— 唯一的残余风险，且**不会自愈**。但 v0.6 把它从"静默以他人身份运行"变成**响亮失败**：token 与成员一一对应，配错会在下一次调用时报 `identity_mismatch`。缓解：① Spike 01 逐条实测绑定（§11，上线阻断项）；② 回执标注归属**与说话人**（由服务端生成，P3），家人当场能发现"你怎么把我的记成你妈了"；③ **审计日志**（§6）让事后追溯成为可能。
  - 结论：身份从"协议性"→"凭据性"（v0.5.2）→ **"结构性 + 可认证"**（v0.6）。浏览侧（查看页）仍是"登录性"的。
- **R2** 拉取式提醒依赖 Agent 开场自觉调 `get_today` → 由 Hermes cron 个人摘要 + 催办兜底（D7）。**v0.6 补正**：cron job 归属某个 profile，运行时自带该 profile 的 token，身份自动确定——**D11 那条"prompt 里写死身份字面值"的约束连同它引入的风险一起消失**。
- **R3** 微信/QQ 通道经桥接实现，稳定性与账号风控风险在 Hermes 侧既有存在——本程序不触碰通道，不因此加重；但提醒触达率受制于此。
- **R4** 程序宕机时 Hermes cron 任务会失败 → 同机部署，单机故障即双双不可用（D2 的代价）；靠管理页健康状态与家人反馈发现。
- **R5** 备份靠纪律 → 管理页一键备份 + Hermes cron 或系统 cron 定期。
- **R6** Agent 理解偏差会直接变成脏数据 → P2/P5/P7 协议约束 + 写操作即时回执供当场纠错 + 软删兜底 + **审计日志**（v0.5.2，§6）让"谁在什么时候改了什么"可追溯。
- **R7** 家人间互相打听安排/待办是常见自然请求，D9 会使程序一律拒绝——Agent 需按 V5 的话术解释"仅本人可见"；若家人因此不满，届时的协商出口是本人把事项建成**全家日程**，而不是放开权限。
- **R8**（v0.6 重写）**身份的可信边界**：v0.6 的身份是"连接 + token"，不是密码学身份（token 是长期有效的共享秘密，无签名、无防重放）。它防的是**模型被诱导冒充他人**与**配置写错**，不防"已经拿到 token 的人"。若日后需要更强的保证，可叠加 mTLS 或短期令牌。
- **R10**（v0.6 新增，**当前最大的落地不确定性**）**每位成员各自一个 bot 凭据 + 一个 Hermes profile，在微信/QQ 上能不能跑通**：微信 iLink 是"扫码得到一个 bot 身份"，多成员就意味着多个 bot 身份、各自扫码、各自被家人添加为联系人；QQ 侧同理。这是 v0.6 唯一"必须先实测再写代码"的假设（Spike 01 第一项），失败则整套身份模型要回退到 v0.5.2 的通道绑定方案。
- **R9**（v0.5.2 新增）查看页与管理页在局域网内**没有 HTTPS**，口令明文经过 Wi-Fi；管理页一个 `ADMIN_PASSWORD` 就能下载整库备份、轮换所有密钥。缓解：仅绑局域网网卡（D2）、强制非默认口令、登录限速、备份文件不落在共享目录。

**开放问题**

- ~~OQ6 家庭是否有共同微信群/QQ 群？~~ —— **v0.5 关闭**。微信侧按不支持处理（iLink bot 身份通常收不到普通微信群事件，§3.3）；QQ 群若日后确认可用只影响 cron 配置项，不影响设计。设计上不再有任何开放阻塞项。
- **OQ7（v0.5 新增）**：程序自身是否需要一条"自检"路径，在启动或管理页里核对"Hermes 配置里各成员的 `channel_overrides` 与 member 表是否一致"？目前只能靠人工比对配置与 member 表。考虑到 R1 的残余风险就是配置写错，这条自检是有价值的；但它需要程序读到 Hermes 的 config.yaml（跨组件耦合）。**建议先用人工 diff（Spike 01 的上线检查项覆盖），顺延至 v0.7 再评估是否自动化。** **v0.6 补充**：自检的对象从"`channel_overrides` 与 member 表是否一致"变成"**每个 profile 配的 token 是否属于正确的人**"——而 v0.6 把这件事**内建**了：token 与成员一一对应，配错会报 `identity_mismatch`（响亮失败），不需要外部自检去发现。仍然需要人工核对的只剩"哪个 bot 凭据属于哪位成员"这一层（Hermes 侧，Spike 01 检查项覆盖）。

**评审结论（2026-10-04）**：v0.4 提出的两处待确认已在 v0.5 落定，记录如下。

- **① V1–V6 对 D9 的落地方式** —— 维持"待办全部个人化、无全家形态（N8）；日程保留全家形态"。理由：给待办加"全家"会凭空多一个共享域，破坏 V1 的简洁性。代价是"这周要买菜"这类高频家务只能建成全家日程，语义上不自然——因此**把 §8.5 的回执纪律推广为全局要求**：Agent 每次写入都要说清落在哪个域（"记成你的个人待办"还是"记成全家日程"）。域选择的**透明度**比域选择的正确性更重要。
- **② V4 的不对称** —— 维持现状，判定合理。个人账本的语义是"这笔钱只有我认"，代记会破坏账本自洽：谁记的和谁花的不一致，后续对账无法解释；待办/日程的代记语义是"我帮你记一下"，天然允许他人代劳。同一动词、两套语义，区别对待是正确的。
