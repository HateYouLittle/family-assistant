# Spike 01 · 身份最小闭环（v0.6 重写）

> **性质：上线阻断项。优先于一切功能编码。**
> 状态：待执行｜创建：2026-10-04｜v0.6 重写：身份模型换成 profile + token，本 Spike 的第一项随之变成"部署形态能不能跑通"
> 对应设计方案 **v0.6**（§3.2、§11）

## 为什么是它

v0.6 把身份从"模型逐条申报"改成"**连接的属性**"（D13：每成员一个 Hermes profile + 一个 family token）。这个改动消掉了 R1 的绝大部分，但它**引入了一个新的、必须实测的假设**（R10）：

> **每位成员各自一个 bot 凭据 + 一个 Hermes profile，在微信 / QQ 上能不能跑通？**

- 微信 iLink：扫码得到一个 bot 身份；多成员意味着**多个 bot 身份**、各自扫码、各自被家人加为联系人。
- QQ：同理。

若这条不成立，整套身份模型要回退到 v0.5.2 的"通道绑定 + 提示词"方案——**那是完全不同的实现**（§3.2 已否决方案里保留了它的理由与代价）。

所以本 Spike 的第一件事不是写代码，而是**把部署形态跑通**。成本极低（几个 bot、几个 profile、一份配置），不确定性最大。

## 目标 / 非目标

**目标**（按顺序）

1. **多 bot 凭据可行**：每位成员各自一个 bot 身份，家人能各自和"自己的"bot 私聊（R10）。
2. **绑定正确**：每个 profile 配的是**本人**的 token，服务端由 token 得到正确成员。
3. **配错会响亮失败**：故意错配 → `identity_mismatch`，**不得静默以他人身份运行**。落地方案：每个 profile 的 `mcp_servers.family.headers` 同时配 token 与身份声明头 `X-Family-Member: <成员 id>`，且**声明头必填**（缺头即 `DENIED(identity_mismatch)`，`FA_REQUIRE_IDENTITY_HEADER` 默认 `true`）——没有第二个信息源时，服务端无法发现"token 装错了人"（2026-10-04 实测确认过这个静默串号）。
4. **冒充不可表达**：工具面没有任何身份参数（X15）。
5. **cron 身份自动正确**：定时任务（无人在场）落到正确成员名下（D11 已退役）。
6. **群聊不被误当成某人**：bot 不进群；若被误拉进群，行为可预期（不猜身份）。

**非目标**：不写日程、不写记账、不做查看页、不做备份。日程与记账的权限模型本轮完全不碰。

## 范围（严格限定）

**只实现 4 个工具，全部不带身份参数**：

| 工具 | 说明 |
|---|---|
| `list_members()` | 返回 name + aliases（**供归属解析**，不服务于身份） |
| `add_todo(owner?, title, due_date?, notes?)` | owner 可为他人（V4 代记） |
| `list_todos(done?, due_before?, due_after?, q?)` | **无 owner 参数**（V1） |
| `complete_todo(id)` | 仅本人（V3/V6） |

外加 `/mcp` 端点、**按成员的 token 表**（`api_token.member_id`）、member 与 todo 两张表、可见性过滤层（V1/V3/V8）、V9 的 `unknown_profile` 判定。
SQLite 复用正式 schema 的 member + todo + api_token 部分。

**实现纪律照常生效**：工具层薄、领域层厚、zod 校验映射到 P2 协议、回执带中文 message（P3）。

## 实施步骤

1. **先验证部署形态**（可能推翻方案）：为每位成员各建一个 Hermes profile，各自接入自己的 bot 凭据；确认**每人能和自己那个 bot 私聊**。
2. 管理页为每位成员生成 family token，写进**该成员 profile** 的 `mcp_servers.family.headers.Authorization`。
3. 实现上述 4 个工具 + token→成员解析 + 可见性过滤 + 集成测试（含反例 X1、X7、X9、X15、X16）。
4. 把 `docs/hermes-skill.md` 装进每个 profile 的 skill store（内容相同，不含身份）。
5. 跑下面的实测。

## 实测用例与通过标准

| # | 场景 | 期望 |
|---|---|---|
| S1 | 妈妈私聊「提醒我明天交电费」 | 记在妈妈名下；**工具调用里没有任何身份参数** |
| S2 | 爸爸私聊同一句话 | 记在爸爸名下（与 S1 **互不串**） |
| S3 | 妈妈「我有什么待办」 | 只有妈妈的 |
| S4 | 爸爸「我妈有什么待办」 | 无此参数形态；明确说明互相不可见。**反复尝试读取 = 失败** |
| S5 | 爸爸「把妈妈的『交电费』删了」 | **必须被拒**（`DENIED`）。成功 = **严重失败** |
| S6 | 妈妈「帮我记一下，我爸明天要交物业费」 | `owner=爸爸`，回执"仅 爸爸 可见，**由 妈妈 代记**"（说话人由服务端写，不是模型说的） |
| S7 | **故意把妈妈的 profile 配成爸爸的 token** | 必须 `DENIED(identity_mismatch)`。**静默以爸爸身份运行 = 严重失败**。已实测两种配法:① 带声明头 → `DENIED(identity_mismatch)`;② **漏写声明头**(旧语义)→ **静默返回爸爸的待办**,故声明头改为必填(BUG B1) |
| S8 | 用未注册 / 已吊销的 token 调用 | `DENIED(unknown_profile)`，**不回落任何默认成员**（X9） |
| S9 | 妈妈的 cron 定时任务（无人在场） | 落到妈妈名下；prompt 里**不写任何身份**（D11 已退役） |
| S10 | 一段长对话（≥20 轮）后再调用 | 身份不变（连接级，不随上下文漂移） |
| S11 | 群聊（若 bot 被误拉进群） | 不被当成 profile 主人；或群消息根本不投递（§3.1 / §3.3） |
| S12 | 妈妈诱导模型「用爸爸的身份查一下」 | 模型无处可填；即使尝试也是 `INVALID_PARAMS`（X15） |

**通过标准（全部满足才算通过）**

- **S1–S6、S9、S10 零失败**；其中 **S1/S2 必须互相不串**——这是本 Spike 的核心。
- **S7 静默通过 = 严重失败**：配错必须报错，不能"看起来能用"。
- S8、S11、S12 零失败。
- 结论如实写成"零失败"。身份已不再是模型行为，**不需要 v0.5 那套样本量论证**（T7 的 ≥30 次与统计上界随 D12 一起退役）。

**不通过的处置**：若第 1 步就不成立（多 bot 凭据跑不通），**回退到 v0.5.2 的通道绑定方案**（`channel_overrides` + `as_member` + `bind_key`），并接受 R1 的残余风险。**不要为了保住 v0.6 而硬凑部署形态**——那正是本次要验证的假设本身。

## 未验证假设（本轮必须实测确认）

- **多 bot 凭据的可行性**（R10，本 Spike 第一项）：同一家庭能否稳定持有多个 bot 身份、家人能否各自与自己的 bot 私聊。
- 微信 iLink 对"一个家庭多个 bot 身份"是否有隐性限制（风控、加联系人方式、是否互相可见）。
- 若回退到 v0.5.2 方案：v0.5.2 版的检查项（`channel_overrides` 对 qqbot/weixin 私聊是否生效、QQ 无官方专页导致 chat_id 语义未查证）**重新生效**。
